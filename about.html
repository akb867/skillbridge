About SkillBridge

A lightweight, organised digital bulletin board for peer-to-peer skill exchange on a campus.

The problem

A large amount of informal teaching happens on any campus, and almost none of it is organised. Students who need help with something specific — debugging a Java loop, understanding operating system scheduling, practising public speaking — have no central place to find someone who can help, and students who could help have no way to say so.

What exists instead is scattered: WhatsApp groups, Telegram channels, a physical notice board outside the department office. Those channels get cluttered fast. A genuine request for help with statistics is buried under forty messages about a fest, and there is no way to search, filter, or come back to it later.

The result is two problems at once:

  • Fragmentation — offers and requests live in different places, so they never meet.
  • Noise — the places they do live in are chronological chat, not a searchable board.

The solution

SkillBridge separates offering from looking for, and makes the board searchable rather than scrollable.

  1. Dual-role listings. Every post is either an offer to teach or a request to learn, colour-coded green and amber throughout, so the two never get confused.
  2. Live filtering. A search box filters as you type across skill, description, category and poster name. Type filters, category chips, a “Mine” toggle and a sort control all combine, with no page reload.
  3. Interactive cards. Each listing is a card. “View Details” opens a dialog; “Connect” opens the same dialog with the contact details already revealed; the card title is a permalink.
  4. Persistence. Listings are written to localStorage on every add and delete, so the board survives refreshes and browser restarts.

The Insights page goes one step further and reports what the board is actually asking for: supply against demand per category, the biggest gaps, and which offers and requests look like they match.

How it is built

Plain HTML, CSS and vanilla JavaScript. No framework, no bundler, no build step, no external dependencies — the site also works when opened directly from the filesystem.

core.js
Shared layer: storage, the saved profile, formatting, card markup, the contact gate, the delete confirmation, and the analytics used by Insights.
app.js
The board page: hero statistics, the posting form and its validation, search, filters, chips, sorting, the details dialog, export and import.
me.js, insights.js, listing.js
Per-page logic for My listings, Insights and the permalink page.
style.css
One stylesheet, themed entirely through CSS custom properties.

Every page shares localStorage because it is scoped to the origin, so the board, your saved details and the analytics all stay in sync without any server.

The project is verified by a headless test harness of 200-odd assertions covering validation, filtering, sorting, deletion, contact masking, export and import, storage edge cases and colour-contrast ratios.

What this is not

Stated plainly, because it matters more than the feature list.

  • It is not a shared database. Data lives in localStorage, which belongs to one browser on one device. Two classmates on two machines see two separate boards. This is the single biggest limitation, and it is a direct consequence of having no backend.
  • It is not authenticated. The saved profile stops you retyping your details. It is not a login, it verifies nothing, and it can be edited from devtools in seconds. A login form bolted onto localStorage would only imitate authentication, so this project does not pretend to have one.
  • Permalinks only resolve locally. A listing link works in the browser that created the listing. Sent to someone else, it lands on “we cannot find that listing” — for the same reason as the first point.
  • There is no moderation. No reporting, no verification of a college email address, no way to remove someone else’s listing. Any of those needs a server.

The natural next step for all four is the same: replace localStorage with a hosted database and real accounts. The front end would barely change — the storage layer in core.js is the only part that would need rewriting.

Privacy and your data

  • Nothing leaves your browser. There are no network requests, no analytics, no third-party scripts and no fonts loaded from a CDN.
  • Contact details are masked by default. A poster’s email or phone number is not written into the page until someone clicks “Reveal contact”, and closing the dialog removes it from the DOM again.
  • Everything is exportable and deletable. Export JSON downloads the whole board; the × on any card deletes that listing after a confirmation; “Not you?” clears your saved details.
  • To erase the app completely, run this in the browser console: 
    localStorage.removeItem('skillbridge_listings');
localStorage.removeItem('skillbridge_profile');
location.reload();
